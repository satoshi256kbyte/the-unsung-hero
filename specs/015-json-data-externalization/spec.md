## User Scenarios & Testing

### User Story 1 - バランス調整担当者がビルド不要で数値を調整できる (Priority: P1)

バランス調整を行う人が、カードのコスト・イベントの発生確率・ステージの予算や
ガントチャート・係数テーブルの値を変更したいとき、対応するJSONファイルの数値を
書き換えてゲームを再読み込みするだけで反映され、TypeScriptのビルド・型チェックを
経る必要がない。

**Why this priority**: 本Specの中核目的（チューニングのイテレーション速度向上）。

**Independent Test**: `public/data/cards/daily.ts` 相当のJSONファイルの `cost` を
書き換えてゲームを再読み込みし、コスト表示が変更後の値になることを確認できる。

**Acceptance Scenarios**:

1. **Given** ゲームが起動している状態、**When** `public/data/cards/デイリー`相当の
   JSONの`cost`値を書き換えて再読み込みする、**Then** 変更後のコストが
   カードの挙動・表示に反映される
2. **Given** ゲームが起動している状態、**When** ステージのガントチャートJSONの
   タスク期間を書き換えて再読み込みする、**Then** 変更後のガントチャートで
   ゲームが開始される
3. **Given** ソースコードを一切変更していない状態、**When** JSONの数値のみを
   変更する、**Then** `npm run build`を実行しなくても変更が反映される

---

### User Story 2 - 開発者がJSONの入力ミスを起動時に検知できる (Priority: P2)

開発者またはバランス調整担当者が、JSONファイルに必須フィールドの記述漏れや
型の異なる値（例: 数値であるべき箇所に文字列）を書いてしまったとき、
ゲームが不正な状態のまま起動するのではなく、起動時に検証エラーとして検知できる。

**Why this priority**: US1でJSON編集の敷居が下がる分、入力ミスの検知が
セーフティネットとして必要になる。

**Independent Test**: カードJSONの`cost`フィールドを削除した状態でゲームを
起動し、正常に起動せずエラーになることを確認できる。

**Acceptance Scenarios**:

1. **Given** カードJSONの必須フィールド（`cost`）が欠落している、
   **When** ゲームを起動する、**Then** 起動時の検証でエラーとなり
   不正なデータのままゲームが開始されない
2. **Given** イベントJSONの確率フィールドに範囲外の値（例: 1.5）が入っている、
   **When** ゲームを起動する、**Then** 起動時の検証でエラーとなる
3. **Given** 全JSONファイルが正しい形式である、**When** ゲームを起動する、
   **Then** 検証エラーなく通常通りゲームが開始される

---

### User Story 3 - 設計ドキュメント・ナレッジグラフの利用者が古い数値に惑わされない (Priority: P3)

設計ドキュメントやナレッジグラフ（グラフDB）で係数・パラメータの情報を確認する人が、
そこに書かれた数値が最新のチューニング結果と食い違っている、という状況に
遭遇しない。数値の生きた実体は常にJSONファイルのみにある。

**Why this priority**: US1でJSON編集が頻繁になるほど、docs/グラフDBに
数値を残す設計だと陳腐化リスクが増す。実装上の変更は小さいため優先度はP3。

**Independent Test**: `docs/03-詳細設計/バランスパラメータ.md`
`カード/*.md` `イベント/*.md` を確認し、係数・コスト・確率の具体的な現在値が
記載されておらず、対応するJSONファイルパスへの参照のみが書かれていることを
確認できる。

**Acceptance Scenarios**:

1. **Given** `バランスパラメータ.md`、**When** 内容を確認する、**Then** 各係数の
   意味・計算式の形・JSON参照先は記載されているが、具体的な現在値は記載されていない
2. **Given** `カード/デイリー.md`、**When** 内容を確認する、**Then** コストの
   具体的な数値（例:「低」等の抽象ラベルを含む）ではなく、JSON参照先が記載されている
3. **Given** グラフDBの`Parameter`ノード、**When** プロパティを確認する、
   **Then** 数値プロパティは持たず、`jsonPath`のような参照プロパティのみを持つ

---

### Edge Cases

- JSONファイルが存在しない（削除されている）場合: 起動時の読み込みエラーとして検知する
  （US2と同様の扱い）
- 効果ロジック（`applyEffect`/`roll`関数）自体はJSON化の対象外であり、
  これらの関数はJSONの値を引数として受け取るだけで、関数の中身を変更する
  ことはJSON編集ではできない（本Specのスコープ外）
- ステージJSONの`conditionalEvents`の条件式（文字列）はJSON化されるが、
  条件式の構文自体（パーサーの実装）は変更しない

## Requirements

### Functional Requirements

- **FR-001**: システムは、各カードのコストをJSONファイルから読み込まなければならない
- **FR-002**: システムは、各イベントの基本発生確率（カード使用時の補正確率を含む）を
  JSONファイルから読み込まなければならない
- **FR-003**: システムは、ステージデータ（メンバー・ガントチャート・条件付きイベント・
  予算等）をJSONファイルから読み込まなければならない
- **FR-004**: システムは、バランス係数テーブル（メンバーパラメータ範囲・進捗ダイス・
  経験値テーブル・パラメータ変動量・閾値・確率テーブル等）をJSONファイルから
  読み込まなければならない
- **FR-005**: システムは、ゲーム開始前に全JSONファイルの内容をスキーマ検証し、
  不正な内容の場合はゲームを開始せずエラーとしなければならない
- **FR-006**: システムは、JSONファイルの変更をソースコードの再ビルドなしに
  反映できなければならない
- **FR-007**: 効果ロジック（カードの`applyEffect`・イベントの`roll`関数の中身）は
  JSON化の対象外とし、TypeScriptのまま維持しなければならない
- **FR-008**: 設計ドキュメント（`docs/03-詳細設計/`配下）は、係数・パラメータの
  意味・計算式の形・対応するJSONファイルへの参照のみを記載し、具体的な現在値を
  記載してはならない
- **FR-009**: ナレッジグラフ（グラフDB）の`Parameter`ノードは、数値プロパティを
  持たず、対応するJSONファイルへの参照プロパティのみを持たなければならない

### Key Entities

- **カードデータ（JSON）**: カード1件分のコスト。`src/game/cards/<name>.ts`の
  効果ロジックと対になる
- **イベントデータ（JSON）**: イベント1種の基本発生確率（カード使用時の補正確率を含む）
- **ステージデータ（JSON）**: ステージ1件分の予算・メンバー・ガントチャート・
  条件付きイベント等
- **バランス係数データ（JSON）**: ステージ・カード・イベントに紐づかない
  横断的な数値テーブル（メンバーパラメータ範囲・進捗ダイス基本範囲・経験値・
  閾値・確率テーブル等）

## Success Criteria

### Measurable Outcomes

- **SC-001**: カードのコストをJSON編集のみで変更し、ソースコードの再ビルドなしに
  ゲームに反映できる
- **SC-002**: 必須フィールドが欠落したJSONで起動を試みた場合、100%の確率で
  起動前にエラーとして検知される（不正な状態のままゲームが開始されない）
- **SC-003**: 既存の単体テスト（Spec-13時点の329件相当）が変更なく全件PASSする
- **SC-004**: `docs/03-詳細設計/バランスパラメータ.md` `カード/*.md` `イベント/*.md`
  に具体的な数値（コスト・確率・係数の現在値）が1件も残っていない
- **SC-005**: 型チェックがエラーゼロで通る

## Assumptions

- 効果ロジックの内容自体（既存の計算式）は変更しない。数値の取得元のみ変更する
- JSONファイルの配置・読み込みタイミング（起動時一括ロードか、遅延ロードか）の
  具体的な実装方式は `/speckit-plan` で決定する
- スキーマ検証に使うライブラリの選定（zod等）は `/speckit-plan` で決定する
- `constants.ts`の`POC_STAGE`のうちステージ固有の重複値（`WORKING_DAYS`等）を
  整理するかどうかの具体的な方針は `/speckit-plan` で決定する
- グラフDBの`Parameter`ノードの数値プロパティ削除・`jsonPath`プロパティへの
  置き換えは、本Spec完了後の`/sync-graphdb`実行時に行う

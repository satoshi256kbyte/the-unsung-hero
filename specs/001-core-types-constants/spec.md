# Feature Specification: Core Types and Constants

**Feature Branch**: `001-core-types-constants`

**Created**: 2026-08-12

**Status**: Draft

## User Scenarios & Testing

### User Story 1 - 後続モジュールが型安全なデータを扱える (Priority: P1)

ゲームロジックを実装する開発者が、メンバー・カード・イベント・ゲーム状態などの
データ構造を型安全に扱えるようになる。
誤った型のデータを渡したときに、実行前にコンパイルエラーで検知できる。

**Why this priority**: すべての後続 Spec（Spec-02〜Spec-10）がこの型定義を前提として
実装される。型が曖昧なまま進めると後続で大規模なリファクタが発生する。

**Independent Test**: 型定義ファイルを import するだけで TypeScript コンパイルエラーが
ゼロになることを確認できる。

**Acceptance Scenarios**:

1. **Given** Member 型が定義されている, **When** 技(skill)に文字列を代入しようとする,
   **Then** TypeScript コンパイルエラーが発生する
2. **Given** GameState 型が定義されている, **When** 必須フィールドを省略して初期化する,
   **Then** TypeScript コンパイルエラーが発生する
3. **Given** CardName の union 型が定義されている, **When** 未定義カード名を使う,
   **Then** TypeScript コンパイルエラーが発生する

---

### User Story 2 - バランスパラメータ変更が一箇所で完結する (Priority: P2)

ゲームデザイナー（またはチューニング担当者）が、進捗確率・イベント発生率・
コスト設定などの数値を変更するとき、1ファイルだけ修正すれば全体に反映される。

**Why this priority**: テストプレイ後のチューニングが多発する想定で、
数値が各所に散在していると修正ミスやバランス崩壊が起きやすい。

**Independent Test**: 定数ファイルの数値を変更し、変更箇所以外をコード修正せずに
テストが通ることで確認できる。

**Acceptance Scenarios**:

1. **Given** 手戻り基本確率が定数として定義されている, **When** 定数値を変更する,
   **Then** その定数を参照するすべての計算に変更が反映される
2. **Given** 週末回復量が定数として定義されている, **When** 心の回復量を変更する,
   **Then** 他のファイルを修正せず変更が反映される

---

### User Story 3 - 技・体の補正値が正しく計算される (Priority: P3)

ゲームエンジンが、メンバーの技レベルと体の値から進捗ダイス補正係数を取得できる。
係数はドキュメント定義のテーブルと完全に一致している。

**Why this priority**: 進捗ダイスエンジン（Spec-03）の正確な動作に直結する。
係数の誤りはゲームバランスを根本から崩す。

**Independent Test**: 技レベルと体の値を入力として係数を計算し、
バランスパラメータ.md のテーブルと一致することをプロパティテストで検証できる。

**Acceptance Scenarios**:

1. **Given** 技レベル 0〜4 の範囲, **When** skill_factor を計算する,
   **Then** 返す乱数範囲が [0.6, 1.2] である
2. **Given** 技レベル 25 以上, **When** skill_factor を計算する,
   **Then** 返す乱数範囲が [0.95, 1.05] である
3. **Given** 体の値 70 以上, **When** health_factor を計算する,
   **Then** 1.0 を返す（補正なし）
4. **Given** 体の値 0〜29, **When** health_factor を計算する,
   **Then** 返す乱数範囲が [0.5, 1.0] である

---

### Edge Cases

- 技レベルが境界値（4/5、9/10、14/15、24/25）のとき、どちらのテーブルが適用されるか
- 体の値が境界値（29/30、49/50、69/70）のとき、どちらのテーブルが適用されるか
- 技レベルが最大値 99 を超えた場合、テーブル参照が範囲外エラーにならないか
- 体の値が 0 の場合、health_factor の下限が適用されるか

## Requirements

### Functional Requirements

- **FR-001**: システムは Member 型を定義しなければならない。
  含むフィールド: 技(skill: 0〜99)、経験値(exp: 0以上)、心(morale: 0〜150)、体(health: 0〜100)
- **FR-002**: システムは Card 型と全カード名の union 型を定義しなければならない。
  カードの種別（即時/セット+自動解除/セット+手動解除）と各カードのコスト定数を含む
- **FR-003**: システムは Event 型を定義しなければならない。
  含む分類: 固定イベント / 条件付きイベント / ランダムイベント（タスク系・メンバー系・プロジェクト系）
- **FR-004**: システムは GanttTask 型と GanttChart 型を定義しなければならない。
  GanttTask は開始ターン・期間・担当メンバーID・現在進捗(%)・状態を持つ
- **FR-005**: システムは GameState 型を定義しなければならない。
  含むフィールド: 現ターン・メンバーリスト・ガントチャート・総消費コスト・予算・手持ちカード・有効エフェクトリスト
- **FR-006**: システムは TurnResult 型を定義しなければならない。
  含むフィールド: 発生イベントリスト・進捗更新リスト・ゲームオーバーフラグ・ゲームオーバー理由
- **FR-007**: システムは StageData 型を定義しなければならない。
  含むフィールド: ガントチャート初期データ・ガントバリアント一覧・条件付きイベントリスト・初期メンバー構成・予算・納期ターン
- **FR-008**: システムは docs/03-詳細設計/バランスパラメータ.md に記載された
  すべての数値定数を定数ファイルに定義しなければならない
- **FR-009**: システムは技レベルを入力として skill_factor の乱数範囲を返す関数を定義しなければならない
- **FR-010**: システムは体の値を入力として health_factor の乱数範囲を返す関数を定義しなければならない
- **FR-011**: すべての型・定数・関数は Phaser および DOM API に依存してはならない

### Key Entities

- **Member**: ゲームメンバー1人を表す。技・経験値・心・体の4パラメータを持つ
- **Card**: PMが使用するカードを表す。名前・コスト・適用方式・効果種別を持つ
- **CardEffect**: カード使用によってセットされる状態を表す。対象・効果種別・残存ターン数を持つ
- **GanttTask**: ガントチャート上の1タスクを表す。進捗状態（通常/停滞/完了）を持つ
- **GanttChart**: ガントタスクの集合。フェーズ構成とバリアント（仕様追加後の差替データ）を持つ
- **GameState**: ある時点のゲーム全体の状態スナップショットを表す
- **TurnResult**: 1ターン実行後の差分情報を表す
- **StageData**: ステージ固有の初期データ一式を表す（ランタイム状態ではなく静的定義）
- **ConditionalEvent**: 条件付きイベントの定義を表す。評価ターン・条件式表現・発生イベント種別を持つ

## Success Criteria

### Measurable Outcomes

- **SC-001**: `tsc --noEmit` がエラーゼロで完了する
- **SC-002**: バランスパラメータ.md に記載されたすべての数値（テーブル値含む）が
  定数として定義されており、マジックナンバーが実装コード中に存在しない
- **SC-003**: skill_factor・health_factor の境界値テストがすべて通過する（Vitest）
- **SC-004**: 型定義ファイルの行数が 300 行以内に収まる（責務の明確な分離）

## Assumptions

- バランスパラメータ.md の数値はすべて「仮値」であり、定数として定義したうえで
  チューニングフェーズで変更される前提
- 型定義はランタイムバリデーション（zod 等）を使わず、TypeScript の静的型のみで表現する
- CardName など union 型の列挙は、現在 docs/03-詳細設計/カード.md に記載されているカードに限定する
- skill_factor・health_factor の「乱数(min, max)」はこの Spec では範囲定数を返すのみで、
  実際の乱数生成は Spec-03（進捗ダイスエンジン）が行う

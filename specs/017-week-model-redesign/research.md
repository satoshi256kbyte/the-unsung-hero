# Phase 0 Research: 週モデル変更（ターン＝暦日・7ターン周期）

Technical ContextにNEEDS CLARIFICATIONはない。主要な決定事項を記録する。

## 1. 曜日判定の実装

**Decision**: `src/game/calendar.ts`に`isWeekend(turn: number): boolean`を
実装する。`(turn - 1) % 7`で0始まりの曜日インデックス（0=月〜6=日）を求め、
5（土）・6（日）を週末とする。

**Rationale**: ターン1=月曜という決定（ADR-025）をそのまま数式に反映する
最小実装。

## 2. `turn.ts`の進捗ダイス変更

**Decision**: ステップ3で、`isWeekend(state.turn)`かつ対象メンバーに
当該週の休日出勇効果（`CardEffect`）が付与されていない場合、そのメンバーの
タスクの進捗ダイスをスキップする（`progressMap`に加算しない）。

**Rationale**: 休日出勤カードの効果は`CardEffect`として`state.activeEffects`
に積まれる既存の仕組み（`effectType`）を再利用できるため、新しい状態管理の
仕組みを追加する必要がない。

## 3. 週末回復のタイミング

**Decision**: `state.turn % 5 === 0`を`(state.turn % 7 === 0)`（日曜終了時点）
に変更する。日曜（ターン7,14,21,...）の処理時に週末回復を適用する。

**Rationale**: 週末回復は「週末の2日間の休息」を表すため、週の最終日（日曜）の
処理タイミングで適用するのが最も自然。月曜開始時点まで遅らせる案も検討したが、
「日曜終了時点で回復済み」の方が実装がシンプル（既存の`turn % N === 0`パターンを
踏襲できる）。

## 4. 休日出勤カードの効果表現

**Decision**: `CardEffect`の`effectType`に新しい値
（例: `"holiday_work_sat"` `"holiday_work_sun"`）を追加し、
`targetId`に対象メンバーのidを設定する。`remainingTurns`は使用した週の
該当曜日ターンまでの残数（例: 火曜に使った場合、次の土曜まで4ターン）とし、
該当日を過ぎたら`applyEffectTick`の既存の減算ロジックで自然消滅させる。

**Rationale**: 既存の`CardEffect`の仕組み（`activeEffects`配列、
`applyEffectTick`によるターンごとの残数管理）をそのまま再利用できる。
新しい状態管理の仕組みを追加しない。

## 5. カードコストの暫定値

**Decision**: 休日出勤（土）・休日出勤（日）のコストは、他の単一メンバー対象
カード（個別面談・表彰・計画休、いずれもコスト2）に合わせて暫定的に2とする。

**Rationale**: 旧`休出`カード（全メンバー対象、コスト6）から「1人だけ対象」に
スコープが縮小したため、単一メンバー対象カードの相場に合わせるのが妥当な暫定値。
最終調整はテストプレイ後に行う。

## 6. 対象選択UIの操作方法

**Decision**: 対象選択が必要なカード（`requiresTarget: true`）をカード枠に
ドロップした直後、その枠の上に対象メンバー一覧（メンバー名のボタン、
`data-testid="target-member-<id>"`）を含む`data-testid="target-picker"`
オーバーレイを表示する。メンバーを1つクリックすると確定し、
オーバーレイは閉じる。対象未選択のままターンを確定した場合、そのカードは
効果が発動しない（`applyEffect`が呼ばれてもtargetId未設定として扱う）。

**Rationale**: 既存のドラッグ&ドロップの操作フローを崩さず、追加の
クリック操作1回だけで対象を選べる最小の実装。

## 7. PoCステージの締切・条件付きイベントの再校正

**Decision**: 新しい週モデルで「22営業日相当」を実現する締切は30ターン
（ターン1=月曜開始として、22営業日目はターン30＝週5の火曜にあたる）。
条件付きイベントの`turn`フィールドは、旧ターン番号（=旧モデルでの
何営業日目か）を新モデルの同じ営業日番目のターン番号に置き換える。

| 旧ターン（旧モデルでの営業日番号） | 新ターン |
| ---------------------------------- | -------- |
| 5 | 5 |
| 10 | 12 |
| 12 | 16 |
| 16 | 22 |
| 18 | 24 |

**Rationale**: 旧モデルはターン番号=営業日番号そのものだったため、
「何営業日目に発生するか」という設計意図を保ったまま、新モデルの
対応するターン番号に機械的に変換できる。具体的な数値の妥当性
（バランス）はテストプレイ後に調整する前提。

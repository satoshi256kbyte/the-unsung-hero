# Feature Specification: カード・イベント・ステージのファイル構造再編

**Feature Branch**: `013-card-event-stage-files`

**Created**: 2026-08-14

**Status**: Draft

## User Scenarios & Testing

### User Story 1 - 新しいカードをファイル1つの追加だけで登録できる (Priority: P1)

ゲーム設計者が新しいカードを追加するとき、コストと効果ロジックをまとめた1ファイルを
`src/game/cards/` 配下に追加し、レジストリに1行importを足すだけで、そのカードがゲーム内で
使用可能になる。既存の `CARD_COSTS` テーブルや共通switch文を編集する必要がない。

**Why this priority**: 現状は `constants.ts` の `CARD_COSTS` と `card.ts` のswitch文という
2箇所を編集する必要があり、更新漏れの原因になっていた。この構造改善がリファクタリングの中核。

**Independent Test**: 新規カードファイルを1つ追加してレジストリに登録し、`applyCards` の
呼び出し結果にそのカードの効果が反映されることをテストで確認できる。

**Acceptance Scenarios**:

1. **Given** 既存の6種の効果ロジック（デイリー・レビュー・モニタリング・個別面談・表彰・計画休）、
   **When** それぞれを対応するカードファイルに移し替える、
   **Then** `applyCards` の入出力は移行前と完全に同じになる
2. **Given** 効果ロジックが未実装の19種のカード、
   **When** コストのみを持つスタブファイルとして作成する、
   **Then** そのカードを渡しても `effectsToAdd` / `memberUpdates` は空のまま
3. **Given** `CardName` のunion型に新しいカード名を追加したが対応ファイルを作り忘れた状態、
   **When** 型チェックを実行する、
   **Then** レジストリの `satisfies Record<CardName, CardDefinition>` によりコンパイルエラーになる

---

### User Story 2 - 新しいランダムイベントをファイル1つの追加だけで登録できる (Priority: P2)

ゲーム設計者が新しいランダムイベントを追加するとき、基本確率と発生ロジックをまとめた
1ファイルを `src/game/events/` 配下に追加し、レジストリに登録するだけで、そのイベントが
毎ターンの抽選対象になる。

**Why this priority**: `EVENT_PROB` テーブルと `event.ts` のswitch文への分散を解消する、
US1と対になる改善。イベント種別に依存しない汎用処理（進捗・メンバーへの適用）はUS1・US2と
独立して共通モジュールに残るため、優先度をUS1の次とする。

**Independent Test**: 新規イベントファイルを1つ追加してレジストリに登録し、
`rollRandomEvents` の呼び出し結果にそのイベントが出現しうることをテストで確認できる。

**Acceptance Scenarios**:

1. **Given** 既存の5種の実装済みイベント（stall・rework・sick・low_motivation・fatigue）、
   **When** それぞれを対応するイベントファイルに移し替える、
   **Then** `rollRandomEvents` の入出力（同一の乱数シードにおける発生イベント）は
   移行前と完全に同じになる
2. **Given** 発生ロジックが未実装の10種前後のイベント、
   **When** 基本確率のみを持ち常に発生しないスタブファイルとして作成する、
   **Then** `rollRandomEvents` の結果に影響を与えない
3. **Given** カード効果による確率補正（例: レビュー使用時のREWORK確率低下）、
   **When** 対象イベントファイルに移し替える、
   **Then** `calcEventProbModifier` を用いた補正結果は移行前と完全に同じになる

---

### User Story 3 - 新しいステージをファイル1つの追加だけで登録できる (Priority: P3)

ゲーム設計者が新しいステージを追加するとき、メンバー・ガントチャート・条件付きイベントを
まとめた1ファイルを `src/game/stages/` 配下に「タイプ-連番」形式（例: `poc-02.ts`）で追加し、
レジストリに登録するだけで、そのステージが選択可能になる。

**Why this priority**: 現状ステージは1件のみで緊急性は低いが、今後複数ステージを追加する際の
土台としてUS1・US2と同じ構造に揃える。

**Independent Test**: `poc-01.ts`（旧`pocStage.ts`）のid・ファイル名を変更し、
既存の参照元（`MainScene.ts`）を更新した状態でも既存のゲームプレイの挙動が変わらないことを
テストで確認できる。

**Acceptance Scenarios**:

1. **Given** 既存の `pocStage.ts`、**When** `stages/poc-01.ts` にリネームし
   `id` を `"poc-01"` に変更する、**Then** `GameEngine` の初期化結果は移行前と完全に同じになる
2. **Given** `stages/index.ts` のレジストリ、**When** `"poc-01"` というidで参照する、
   **Then** `poc-01.ts` の `StageData` が取得できる

---

### User Story 4 - バランス調整担当者がカード・イベントの内容をファイル単位で編集できる (Priority: P2)

バランス調整を行う人が、特定のカード・イベントの説明やパラメータを確認・修正したいとき、
`docs/03-詳細設計/カード/` `docs/03-詳細設計/イベント/` 配下の該当ファイル（日本語ファイル名）
だけを開けばよく、他のカード・イベントの内容と混在した長大な表を探す必要がない。

**Why this priority**: ソースコード側の構造改善と対になる、人手作業の効率化。
ゲームロジックの外部挙動には影響しないため、優先度はUS1と同列のP2とする。

**Independent Test**: `docs/03-詳細設計/カード.md` の該当行を
`docs/03-詳細設計/カード/<カード名>.md` に移した内容が、元の表の内容と一致することを
目視で確認できる。

**Acceptance Scenarios**:

1. **Given** 既存の `カード.md` の表（約26行）、**When** 各行を対応するファイルに分割する、
   **Then** 元の表にあった情報（効果・適用方式・コスト（仮）・説明）が過不足なく
   個別ファイルに転記されている
2. **Given** 既存の `イベント.md` の各表（プロジェクト・タスク・メンバー、約23件）、
   **When** 各行を対応するファイルに分割する、
   **Then** 元の表にあった情報（効果・種別・カテゴリ・説明）が過不足なく個別ファイルに
   転記されている
3. **Given** `カード.md` `イベント.md` の横断的な説明（分類・適用方式・リスクグラフ・
   固定イベント・手戻り停滞・未決定事項）、**When** 分割を行う、**Then** これらの説明は
   `カード.md` `イベント.md` に残ったままである

---

### Edge Cases

- 既存のswitch文にあったが `CardName` / イベント一覧に対応する定義が今は存在しない場合:
  対象外として扱う（本リファクタリングでは新規カード・イベントの追加は行わない）
- 同じ効果ロジックが複数箇所から参照されるヘルパー関数（例: `calcEventProbModifier` を
  呼び出す複数のイベント）: 各イベントファイルが個別にヘルパーをimportして良い
  （共通ヘルパー自体の移動は本リファクタリングの対象外）
- ステージレジストリに存在しないidを指定した場合: 本Specの対象範囲外
  （呼び出し側での検証は既存のまま。エラーハンドリングの追加は行わない）

## Requirements

### Functional Requirements

- **FR-001**: システムは、各カードのコストと効果ロジックを `src/game/cards/` 配下の
  1ファイルにまとめて定義しなければならない
- **FR-002**: システムは、`cards/index.ts` のレジストリを介してカード名からカード定義を
  解決しなければならない（`CARD_COSTS` テーブルは廃止する）
- **FR-003**: システムは、`CardName` のunion型に対しレジストリが
  `satisfies Record<CardName, CardDefinition>` により網羅性を検証しなければならない
- **FR-004**: システムは、各ランダムイベントの基本確率と発生ロジックを
  `src/game/events/` 配下の1ファイルにまとめて定義しなければならない
- **FR-005**: システムは、`events/index.ts` のレジストリを介して `rollRandomEvents` を
  実行しなければならない
- **FR-006**: システムは、イベント種別に依存しない汎用適用処理
  （`applyEventToProgress` / `applyEventToMember`）を共通モジュールとして維持しなければならない
- **FR-007**: システムは、条件式評価（`evaluateCondition`）を共通モジュールとして
  維持しなければならない（分割対象としない）
- **FR-008**: システムは、各ステージのデータ（メンバー・ガントチャート・条件付きイベント）を
  `src/game/stages/` 配下の1ファイルにまとめて定義しなければならない
- **FR-009**: システムは、ステージファイル名を「タイプ-連番」形式（例: `poc-01`）とし、
  `StageData.id` と一致させなければならない
- **FR-010**: システムは、`stages/index.ts` のレジストリを介してステージidから
  `StageData` を解決できなければならない
- **FR-011**: システムは、効果ロジックが未実装のカード・イベントについて、
  コスト／基本確率のみを持ち効果が空である定義として作成しなければならない
- **FR-012**: 本リファクタリングの前後で、既存のゲームロジックの外部から見た振る舞い
  （`processTurn` 等の入出力）が変化してはならない
- **FR-013**: システムは、`docs/03-詳細設計/カード.md` の個別カードの内容を
  `docs/03-詳細設計/カード/<カード名>.md`（日本語ファイル名）に分割しなければならない
- **FR-014**: システムは、`docs/03-詳細設計/イベント.md` の個別イベントの内容を
  `docs/03-詳細設計/イベント/<イベント名>.md`（日本語ファイル名）に分割しなければならない
- **FR-015**: `カード.md` `イベント.md` は分割後も横断的な説明（分類・適用方式・
  リスクグラフ・固定イベント・手戻り停滞・未決定事項）を保持しなければならない
- **FR-016**: `docs/03-詳細設計/カード/` `イベント/` 配下には、一覧・索引を兼ねるファイルを
  作成してはならない
- **FR-017**: システムは、既存のPoCステージのガントチャート・条件付きイベントを
  `docs/03-詳細設計/ステージ/PoCステージ01.md` に表形式で記載しなければならない。
  ガントチャートの表は各タスクの担当メンバー名を含めなければならない

### Key Entities

- **CardDefinition**: カード1件分の定義。コスト（`cost: number`）と効果適用関数
  （`applyEffect(state): { effectsToAdd, memberUpdates }`）を持つ
- **EventDefinition**: ランダムイベント1種の定義。`roll(state, activeEffects): GameEvent | null`
  を持つ
- **StageData**: 変更点として `id` の命名規則を「タイプ-連番」形式に統一する
  （既存フィールドは変更しない）

## Success Criteria

### Measurable Outcomes

- **SC-001**: 既存の単体テスト（`card.test.ts` `event.test.ts` `conditional.test.ts`
  `engine.test.ts` 等、リファクタリング後にファイル移動する場合は移動後のテスト）が
  全件PASSする
- **SC-002**: 型チェック（`npm run typecheck`）がエラーゼロで通る
- **SC-003**: 新しいカードを1つ追加する変更が、`cards/` 配下への1ファイル新規作成と
  レジストリへの1行追加のみで完結する（既存カードファイルの編集が不要）
- **SC-004**: `card.ts` `event.ts` がリポジトリから削除されている
  （`cards/index.ts` `events/index.ts` に統合済み）
- **SC-005**: `docs/03-詳細設計/カード.md` の分割前後で、個別カードの情報が
  1件も欠落していない（行数ベースで全26件が対応するファイルに存在する）
- **SC-006**: `docs/03-詳細設計/イベント.md` の分割前後で、個別イベントの情報が
  1件も欠落していない（プロジェクト7・タスク9・メンバー7の全23件が対応するファイルに存在する）

## Assumptions

- 効果ロジックの内容自体（既存6種のカード・5種のイベントの具体的な計算式）は変更しない。
  ファイルの配置場所を移すのみ
- 未実装のカード19種・イベント10種前後について、効果ロジックの新規実装は本Specでは行わない
  （空のスタブとする）
- `docs/` 側の再編（カード・イベント・ステージのドキュメント分割）は本Specのスコープに含む
- ステージファイルのリネーム（`pocStage.ts` → `poc-01.ts`）に伴う既存の参照元
  （`MainScene.ts` 等）の修正は本Specに含む
- 既存の単体テストファイル（`card.test.ts` `event.test.ts`）を新しいディレクトリ構造に
  合わせて再編するかどうかの具体的な方針は `/speckit-plan` で決定する
- PoCステージ以外の新規ステージの追加は本Specのスコープに含まない
  （構造の土台を作るのみ）

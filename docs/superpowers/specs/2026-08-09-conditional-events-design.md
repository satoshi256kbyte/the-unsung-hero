# 条件付きイベント設計

## 概要

ステージのイベントを3分類に拡張し、「条件付きイベント」を新設する。
条件付きイベントはステージデータ（レベルデータ）に事前定義され、
指定ターンに条件を評価し、満たせば発生、満たさなければ永久に消滅する。

## 背景・動機

従来の設計ではスコープ変更やメンバー離脱などの大イベントもランダム抽選で発生していた。
これをステージデータとして事前設計することで以下を実現する：

- ステージごとに意図的な難易度カーブやドラマを設計できる
- プレイヤーの行動（カード使用・KPI維持）が大イベントの回避に直結する
- 同じステージを繰り返しプレイした際に、前回の学びを活かせる

## イベントの3分類

| 分類 | 説明 | 例 |
|------|------|-----|
| 固定イベント | タイミングが確定。従来どおり | キックオフ・デイリー・週次進捗会議・締め・クロージング |
| 条件付きイベント | ステージデータに事前定義。指定ターンに条件を評価し、満たせば発生、満たさなければ消滅 | 追加要望・仕様変更・値下げ要求・離脱・応援要員 |
| ランダムイベント | 毎ターンのリスクグラフ確率に基づく抽選。従来どおり | 手戻り・停滞・体調不良・ひらめき |

## 条件付きイベントの対象

現在の「ランダムイベント」から以下を条件付きイベントに移行する。

### 条件付きに移行するイベント

- プロジェクトイベント: 追加要望、仕様変更、値下げ要求、監査対応、検収不合格、追加予算承認、早期検収
- メンバーイベント: 離脱、応援要員

### ランダムのまま残すイベント

- タスクイベント: 手戻り、ブロッカー発生、仕様不明確、環境障害、ひらめき、一発合格、
  過大報告発覚、過小報告発覚、報告漏れ
- メンバーイベント: 体調不良、モチベーション低下、疲労蓄積、休息、地元優勝

## 条件付きイベントのデータ構造

ステージデータ内に以下の構造で定義する。

| フィールド | 説明 |
|-----------|------|
| id | ステージ内で一意の識別子 |
| turn | 判定ターン番号 |
| condition | 発生条件（論理式） |
| event | 発生するイベント名（既存のイベント表から参照） |
| params | イベント固有パラメータ（対象メンバー指定、追加タスク内容など） |

## 条件式で参照可能なパラメータ

| カテゴリ | パラメータ例 |
|---------|-------------|
| EVM指標 | SPI, CPI, EV, AC, PV |
| メンバー状態 | avgMorale（平均心）, avgHealth（平均体）, memberCount |
| 特定メンバー | member('名前').心, member('名前').体 |
| 進捗 | taskCompletionRate, phaseProgress('工程名') |
| 経過 | currentTurn |
| カード使用履歴 | cardUsed('カード名'), cardUsedCount('カード名') |
| 論理演算 | &&, ||, !, 比較演算子（>=, <=, ==, !=, >, <） |

## 具体例（3ヶ月ステージ）

```json
[
  {
    "id": "ev01",
    "turn": 15,
    "condition": "SPI >= 0.95",
    "event": "追加要望",
    "params": {"tasks": ["画面A追加"]}
  },
  {
    "id": "ev02",
    "turn": 30,
    "condition": "cardUsed('残業許可') && avgMorale < 40",
    "event": "離脱",
    "params": {"target": "lowest_morale"}
  },
  {
    "id": "ev03",
    "turn": 45,
    "condition": "CPI >= 1.1 && taskCompletionRate >= 0.7",
    "event": "追加予算承認",
    "params": {"amount": 500}
  },
  {
    "id": "ev04",
    "turn": 20,
    "condition": "!cardUsed('モニタリング')",
    "event": "仕様変更",
    "params": {"affectedPhase": "設計"}
  }
]
```

## 判定ルール

- 判定は指定ターンのみ実施する。条件を満たさなければそのイベントは永久に消滅する
- プレイヤーには条件付きイベントの存在・条件・タイミングは一切公開されない。
  発生して初めてわかる
- 条件付きイベントはリスクグラフの確率表示の対象外
  （発生するかしないかの二値であり、確率分布ではないため）

## ターン処理フローへの組み込み

既存のステップ4（固定イベント判定）とステップ5（その他のランダムイベント抽選）の間に挿入する。

```
4.   固定イベント判定
4.5  条件付きイベント判定 【新設】
     → 当ターンに判定対象の条件付きイベントがあるか確認
     → あれば条件式を評価
     → 条件を満たせば発生キューに追加、満たさなければ消滅
5.   その他のランダムイベント抽選
6.   イベント結果の適用（条件付きイベントの結果もここで一括適用）
```

## ステージデータの構成

ステージは以下を含むレベルデータとして事前設計される。

- ガントチャート（タスク構成・依存関係・期間）
- 条件付きイベントリスト
- 初期メンバー構成
- 予算・納期

## 既存設計への影響

| 変更対象 | 内容 |
|---------|------|
| イベント.md | 3分類の導入、条件付きイベントセクション新設、対象イベントの再分類 |
| ターン処理フロー.md | ステップ4.5の挿入 |
| 要件定義/index.md | ステージデータの構成にガントチャート＋条件付きイベントが含まれる旨の追記 |

変更しないもの：

- イベントカテゴリ（ガントチャート計算との対応）
- リスクグラフの仕組み
- 固定イベント（キックオフ・締め等）
- ランダムイベントの抽選ロジック

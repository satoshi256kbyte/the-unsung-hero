# プレイテスト用Claude Codeスキル設計書

## 目的

このスキルは、実装されたゲームエンジンに対してPM役のプレイヤーとして1ステージを実際にプレイし、
「ターンごとに先読みなしで対処する」という設計意図通りのプレイスタイルでどこまで結果が変わるかを検証し、
バランス調整のための改善点を報告することを目的とする。

[要件定義](../01-要件定義/index.md) の想定バランスは、
「ターンごとに先読みなしでそのまま対処法を打つ感じだとギリギリ納品できるくらい」である。
この想定が実際の数値・確率設定で成立しているかどうかは、
実装が固まった段階で実プレイを重ねて検証する必要がある。
人間のプレイテストだけに頼ると母数が確保しづらいため、
Claude Codeのスキルとして自動プレイ・自動レポートの仕組みを用意する。

## 背景・前提

現時点（本ドキュメント執筆時点）では、ゲーム本体は設計メモがあるのみで、
実装（ゲームエンジン・UI）はまだ存在しない。

本スキルは、ゲームエンジンの実装が完了し、プログラムから操作可能なインターフェース
（「前提条件」節を参照）が用意された段階で利用できることを前提とした設計であり、
現時点では実装できない（＝ゲームエンジンの完成が前提の後追い実装になる）。

## スキルが解決する課題

- 人手によるプレイテストは1回あたりのコストが高く、試行回数を確保しにくい。
  カード・イベントの確率調整のように「何十回もプレイして分布を見る必要がある」調整には向かない
- 開発者自身がテストプレイすると、無意識にランダムイベントの結果を先読みしたり、
  詰みそうな回だけやり直したりしてしまい、
  「先読みなし・一発勝負」という想定プレイ条件を再現しにくい
- 上記より、「先読みなし・やり直しなし」のプレイ方針を機械的に厳守できるプレイヤーとして
  Claude Codeエージェントを使い、大量の試行結果からバランス上の課題を洗い出す

## 前提条件（ゲームエンジンに必要なインターフェース）

本スキルは、以下のインターフェース（CLIまたはAPI、形式は問わない）を持つゲームエンジンが
存在することを前提とする。エンジン自体の実装は本設計書のスコープ外だが、
スキルが動作するために必要な最低限の契約をここに明記する。

| 操作 | 入力 | 出力 |
|------|------|------|
| new-stage | 期間（1/3/6/12ヶ月）、乱数シード | 初期状態（ガントチャート・PERT図・EVM・リスクグラフ・初期配布カード） |
| get-state | なし | 現在ターン時点の状態一式（4ツールの表示内容、手持ちカード、直近の発生イベントログ） |
| play-turn | 使用するカードと対象のリスト | ターン進行結果（更新後の状態、当該ターンの固定/ランダムイベント内訳、コスト消費内訳） |
| get-result | なし | ステージ終了時点の結果（クリア／失敗、最終利益、失敗理由） |

get-state・play-turnの応答には、その時点で確定していない未来の情報
（次ターン以降のランダムイベントの結果など）を一切含めないこと。
これが「先読みなし」を成立させるための最重要条件であり、エンジン側の実装責任とする。

## スキルの責務

1つの乱数シードに対して1ステージ分のプレイを最初から最後まで自動で実行し、
プレイログとバランス上の気づきを構造化データとして出力する。

- 実行するのはあくまで「1回のプレイ」。詰みそうになっても巻き戻さない、
  複数のプレイ方針を試して良い方を選ぶといったこともしない（詳細は次節）
- ステージ終了（クリア／失敗）まで自律的にターンを進める
- 各ターンの意思決定理由を簡潔にログへ残す（レポート作成時の根拠にするため）

## プレイ方針（意思決定ポリシー）

先読みなしでのプレイを徹底するための行動ルール。

- その時点の get-state から得られる情報（ガントチャート・PERT図・EVM・リスクグラフ・
  手持ちカード・直近イベントログ）のみを判断材料にする
- 一度確定させたターンの選択はやり直さない。結果が悪くてもそのまま次のターンに進む
- デフォルトはPMの理想形（デイリー・レビュー・モニタリング・サマライズ）を維持し、
  リスクグラフの悪化やメンバーの状態変化など明確なシグナルが出たときのみ理想形から入れ替える。
  「なんとなく強そうだから」で理想形を崩さない
- 交渉・強制締めなどハイリスク調整系のカードは、
  ガントチャート未完了のまま締切／締めが迫っているなど、
  使わないと詰むことが明確な場面でのみ使用する
- 判断に迷うケース（ルールが未決定・複数の解釈が可能）に遭遇した場合は、
  最も保守的な（安全側の）解釈を採用し、その旨をログに残す

## 実行フロー

1. new-stage でステージを開始する（期間・シードを指定する）
2. get-state で現在の状態を取得する
3. プレイ方針に基づき、当日使用するカードを決定する（合計コストが1日の上限を超えないこと）
4. play-turn でターンを実行する
5. ステージが終了していなければ2に戻る
6. ステージ終了後、get-result で最終結果を取得する
7. ターンごとのログと最終結果から、プレイレポートを生成する

## 出力・レポート仕様

レポートは大きく2部構成とする。

### プレイサマリー

| 項目 | 内容 |
|------|------|
| ステージ条件 | 期間・乱数シード |
| 結果 | クリア／失敗、失敗した場合はその理由 |
| 利益 | 最終利益と目標利益との差分 |
| 納期の余裕 | 完了ターンと締切ターンの差 |
| コスト消費 | EVMの主要指標（PV/EV/AC）の最終値と推移概要 |
| イベント発生状況 | 固定イベント・ランダムイベントの発生回数一覧 |

### 改善点一覧

| カテゴリ | 内容例 |
|---------|--------|
| バランス（数値） | 特定カードのコストが割に合わず一度も使う場面がなかった、特定のネガティブイベントの発生確率が高すぎるなど |
| バランス（詰みやすさ） | 保守的なプレイでも詰んだ／逆に楽勝だったなど、想定難易度（ギリギリ納品）との乖離 |
| ルールの曖昧さ | プレイ中に解釈が割れた、ドキュメントに記載がなかった箇所 |
| 情報設計 | ガントチャート・PERT図・EVM・リスクグラフの情報だけでは意思決定に不足していた箇所 |

各改善点には、根拠となったターン番号・状態のスナップショットを添えて再現性を持たせる。

## 統計的評価（複数回実行）

1回のプレイはランダム要素に強く左右されるため、単発の結果だけでバランスを判断しない。
同一ステージ条件で乱数シードを変えて複数回（目安10〜30回）実行し、
クリア率・平均利益・平均余裕日数などを集計してから改善点を挙げることを基本とする。

- 複数回実行は、まず本スキルをループ実行（`/loop` スキルでの反復、
  またはシード違いでの連続実行スクリプト）でまかなう
- 実行回数が多く並列化したい場合は、Workflowツールで複数シードを並列プレイし
  結果を集計するという拡張も考えられる
  （本設計書では拡張案として記載するのみで、実装方針は確定しない）

## 非対象範囲・制約

- ゲームエンジン本体の実装はこのスキルのスコープ外（別途必要）
- UI／見た目の検証は対象外（数値・確率・ルールのバランスのみを対象とする）
- 人間プレイヤーが行うような「あえて理想形を崩して博打を打つ」攻めのプレイスタイルの検証は対象外。
  あくまで「保守的・先読みなし」の基準ラインを測ることが目的

## 未決定・要検討事項

- ゲームエンジンのインターフェース（CLIかHTTP APIか、状態のシリアライズ形式）の確定
- 「理想形からの入れ替え判断」のプレイ方針をどこまで具体的なルールとして明文化するか
  （曖昧だとプレイ結果の再現性が下がる）
- 複数回実行時の集計指標の確定（クリア率、平均利益、利益の分散など）
- レポートのフォーマット（Markdown／JSON等）と保存先
